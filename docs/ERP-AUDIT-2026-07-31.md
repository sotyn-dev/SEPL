# SEPL ERP — Bug & UI/UX Audit

**Date:** 31 July 2026
**Branch audited:** `feature/spos-execution-system` (HEAD `93301051`)
**Scope:** 85 client pages, 61 server route files, ~271 source files
**Method:** static code analysis (pattern sweep + targeted code reading). **No runtime/browser testing was performed** — every finding below is traceable to a file and line, but severity of user impact is an estimate, not an observed failure.

---

## 1. Executive summary

The ERP is structurally healthy in the areas that usually rot first: there is a global `AppErrorBoundary` wired to Sentry, a shared toast system (1,439 usages — no `alert()` anywhere in the app), gzip compression, and consistent async error handling on the server (no route file has unguarded `async` handlers).

The problems are concentrated in three places:

| # | Theme | Severity | Rough effort |
|---|-------|----------|--------------|
| A | **Authorisation gaps** — 15 route files with write endpoints and zero `requirePermission` | 🔴 Critical | 3–5 days |
| B | **Mobile parity** — 60+ pages render a desktop-only `<table>` with no mobile card | 🟠 High | 5–8 days |
| C | **Modal accessibility & UX** — no Escape key, no focus trap, no `role="dialog"` app-wide | 🟠 High | 0.5 day (shared component) |
| D | Login has no rate-limit / lockout | 🔴 Critical | 0.5 day |
| E | 29 pages with tables that can't scroll horizontally | 🟡 Medium | 1–2 days |
| F | 18 pages fetch data with no loading state | 🟡 Medium | 1–2 days |
| G | Unbounded `SELECT *` list queries (26) | 🟡 Medium | 2 days |
| H | 121 native `confirm()` dialogs | 🟢 Low | 2 days |

Items A and D overlap with the existing whole-backend security audit already on record; this pass confirms they are still open on this branch.

## 2. Critical findings

### A. Write endpoints with no permission check

`authMiddleware` proves *who* you are; it does not prove *what you may do*. These 15 route files mount only `authMiddleware` — any logged-in user, including a Viewer, can hit every write endpoint in them.

| Route file | Write endpoints | Notes |
|---|---|---|
| `server/routes/quotations.js` | 19 | includes `DELETE /:id`, `POST /po-foc/:id/approve`, labour-rate import/merge |
| `server/routes/installation.js` | 19 | RA bills, MB bills, handover, payments — all financial |
| `server/routes/delegations.js` | 12 | |
| `server/routes/pmstasks.js` | 9 | |
| `server/routes/champions.js` | 7 | leaderboard/score writes |
| `server/routes/support.js` | 6 | |
| `server/routes/emailRules.js` | 5 | persistent config — see note below |
| `server/routes/announcements.js` | 4 | broadcast to all users |
| `server/routes/push.js` | 4 | |
| `server/routes/auth.js` | 17 | user CRUD — has its own admin gates, verify individually |
| `server/routes/indentfms.js` | 3 | |
| `server/routes/raci.js` | 3 | |
| `server/routes/dashboards.js` | 1 | |
| `server/routes/backups.js` | 1 | DB backup trigger |
| `server/routes/publicHr.js` | 1 | intentionally public — confirm |

**Worst two, verified by reading:**

- [quotations.js:9](server/routes/quotations.js:9) — `router.use(authMiddleware)` is the only gate. [quotations.js:535](server/routes/quotations.js:535) is `POST /po-foc/:id/approve`: **any logged-in user can approve a PO/FOC.**
- [installation.js:5](server/routes/installation.js:5) — same pattern. [installation.js:175](server/routes/installation.js:175) `POST /payments` and [installation.js:43](server/routes/installation.js:43) `POST /ra-bills` write money records with no role check.

**Fix:** add `requirePermission('<module>', 'create'|'edit'|'delete')` per endpoint, mirroring the pattern already used in `procurement.js` / `collections.js`. Approve-type endpoints additionally need a `canApprove()` identity check, not just a module permission — approving your own submission is a segregation-of-duties failure even with the permission granted.

### D. No brute-force protection on login

`server/lib/rateLimit.js` exists but is used by exactly one file, `server/routes/siteChat.js`. [auth.js:43](server/routes/auth.js:43) logs failed attempts for later inspection but does not throttle, delay, or lock.

**Impact:** unlimited password guessing against every account, including admin. Combined with the known default-JWT-secret issue, this is the most exposed part of the system.

**Fix:** apply the existing `rateLimit` middleware to `POST /auth/login` (suggest 5 attempts / 15 min per IP + per username), and add a progressive delay or temporary lock after 10 failures.

### Related: CORS is disabled, not configured

[index.js:26-29](server/index.js:26) sets `origin: false` in production. That blocks cross-origin browser requests entirely — fine while the API and client are served from one origin, but it means any future mobile web app or subdomain silently breaks with an opaque CORS error rather than a clear config change. Worth an explicit allowlist instead.

## 3. UI/UX findings

### B. Mobile parity — the recurring class

This is the fourth time this bug class has surfaced. **60 pages** contain a `<table>` and no `md:hidden` mobile card, meaning on a phone the user sees either a clipped table or nothing usable.

Excluding the ~15 `*Print.jsx` pages (print layouts — desktop/PDF only, correctly excluded), the real list of affected working pages is ~45, including high-traffic ones:

`Collections` · `Customers` · `Vendors` · `Expenses` · `SalesBilling` · `Snags` · `HelpTickets` · `Leads` · `ItemMaster` · `RentalTools` · `SubContractors` · `Complaints` · `CompanyAssets` · `ChequeFMS` · `IndentFMS` · `Estimator` · `Scorecard` · `HR` · `HRSystem` · `Checklists` · `CashFlow` · `ArApTracker` · `Installation` · `Billing` · `BusinessBook` · `CRMFunnel` · `CRMKitting` · `PriceRequired` · `ProcurementSchedule` · `SolarProjects` (+ 5 other Solar pages) · `Tools` · `Influencers` · `LabourRate` · `EmailTriggers` · `FireNoc` · `WeeklyScore` · admin: `AuditLog` · `UserManagement` · `RolesPermissions` · `Locations` · `DatabaseBackups` · `CollectionsMD`

**Note:** the standing rule from prior fixes is *mirror every desktop control to the mobile card*. Here the card itself is missing, which is the stronger version of the same failure. `Delegation.jsx` is intentionally table-only and should stay that way.

**Recommendation:** rather than 45 hand-written cards, build one `<ResponsiveTable columns={} rows={} actions={} />` component and migrate pages into it. That converts a recurring bug class into a single fixable component and prevents the fifth occurrence.

### C. Modal has no keyboard or screen-reader support

[components/Modal.jsx](client/src/components/Modal.jsx) — the shared modal used across the app:

- No `Escape` key handler — the only way out is clicking the ✕ or the backdrop
- No focus trap and no focus restore on close — Tab walks into the page behind the overlay
- No `role="dialog"` / `aria-modal="true"` / `aria-labelledby` — screen readers do not announce it as a dialog
- No `overflow: hidden` on `<body>` — the page behind scrolls under the modal on mobile

Because this is a shared component, one fix (~30 lines) repairs every modal in the ERP. High value-to-effort ratio — do this first among the UX items.

Separately, **11 pages hand-roll their own overlay** with raw `fixed inset-0` instead of using `<Modal>`: `Attendance`, `Complaints`, `CRMKitting`, `FireNoc`, `ItemMaster`, `QualificationChat`, `RentalTools`, `SolarFunnel`, `SolarProjects`, admin `AuditLog`, admin `WordCount`. These will not inherit the fix. Migrate them.

### E. Tables that cannot scroll on narrow screens

29 files render a `<table>` with no `overflow-x-auto` wrapper anywhere in the file. On a phone or a narrow window the table is clipped with no way to reach the right-hand columns — including the action buttons, which are usually last.

Worst offenders by table count: `DashboardWarRoom.jsx` (11 tables), `DeliveryNotePrint.jsx` (6), `Billing.jsx` (5), `Employees.jsx` (4), `DashboardCMDToc.jsx` (3). Print pages in this list are acceptable; the dashboards and `Billing`/`Employees`/`Orders`/`Quotations`/`Customers`/`Complaints` ones are not.

### F. Missing loading states

18 pages call `useEffect` to fetch data but contain no loading indicator. The user sees an empty table for the duration of the request and cannot tell "still loading" from "no data" — a frequent source of "the page is blank" reports.

`ArApTracker` · `Billing` · `BusinessBook` · `ChequeFMS` · `Complaints` · `Expenses` · `IndentFMS` · `Influencers` · `Installation` · `Leads` · `Quotations` · `Vendors` · `SolarFunnel` · `SolarLabourMaster` · `SolarMaterialMaster` · `SolarProjects` · `SolarQuotation` · `SolarRateMaster`

The Solar module accounts for 6 of the 18 and also dominates the missing-empty-state list below — it appears to have been built without the conventions the rest of the app follows.

### Missing empty states

6 non-print pages render a table with no "no records" message: all five `Solar*` pages plus `SolarQuotation`. Same root cause as above.

### H. 121 native `confirm()` dialogs

`window.confirm` is used 121 times across 25+ pages (`Procurement.jsx` alone has 16). These are unstyled, cannot be branded, block the JS thread, are suppressible by the browser, and read poorly on mobile. The app already has a toast system and a `Modal` component — a `useConfirm()` hook returning a promise would replace all 121 call sites with the same one-line ergonomics.

### Form double-submit

46 pages have form/save handlers; only 30 reference a `saving`/`submitting` guard. The remaining ~16 allow a double-click to fire two POSTs — on financial forms (bills, payments, indents) that means duplicate records.

### Accessibility baseline

- 889 `<input>` elements, 7 `aria-label` attributes. Most inputs rely on adjacent text rather than an associated `<label htmlFor>`, so screen readers and click-to-focus don't work.
- 811 `title=` attributes suggest heavy use of icon-only buttons. `title` is a tooltip, not an accessible name — these need `aria-label` as well.

### Date/time correctness

22 call sites across 11 files still use raw `new Date(...).toLocale*` instead of the project's `utils/datetime.js` helpers: `Attendance`, `Checklists`, `Dashboard`, `DashboardCMD`, `DashboardCMDToc`, `DashboardWarRoom`, `DPR`, `IndentPrint`, `Procurement`, `SolarQuotation`, admin `Locations`.

DB timestamps are UTC. Raw `toLocale*` renders in the *browser's* timezone, which is IST on all current machines — so this is latent, not currently visible. It becomes a live bug the moment anyone opens the ERP from a different timezone or a device with a wrong clock, and it silently shifts dates near midnight. Worth cleaning up while it's cheap.

## 4. Performance / data-integrity findings

### G. Unbounded queries

26 `SELECT * FROM ...` statements with neither `WHERE` nor `LIMIT`. These load whole tables into memory on every request. Harmless at current data volume; they degrade linearly and will be the first thing to slow down as `attendance`, `audit_log`, and `dpr` grow. Only 19 of 85 pages implement pagination despite a `Pagination.jsx` component existing.

### Dynamic SQL

106 sites build SQL with template interpolation. **I found no SQL injection** — reviewing them, the interpolated values are consistently either internal identifiers (`PRAGMA table_info(${t})` over a hardcoded table list), whitelisted column names built from server-side arrays (`SET ${sets.join(', ')}` with values passed as bound params), or `?` placeholder strings generated from array length. This matches the earlier backend audit's conclusion.

Two spots deserve a second look because the interpolated value is an ID list rather than placeholders:
- [businessbook.js:378-383](server/routes/businessbook.js:378) — `IN (${ids})` in six consecutive `DELETE` statements
- [orders.js:44](server/routes/orders.js:44) — `UPDATE ${table} SET ${column}=NULL`

Both appear to derive their input server-side, but they are destructive operations and should use bound parameters on principle.

### `.toFixed()` on possibly-null values

66 call sites. Most are guarded. Unguarded ones that will throw `TypeError` if the field is null — which blanks the whole page, since it happens during render:
- [Attendance.jsx:295](client/src/pages/Attendance.jsx:295) and [:780](client/src/pages/Attendance.jsx:780) — `location.latitude.toFixed(6)` with no null check
- [admin/Locations.jsx:340](client/src/pages/admin/Locations.jsx:340) and [:620](client/src/pages/admin/Locations.jsx:620) — same pattern on `u.latitude` / `p.latitude`
- [CashFlow.jsx:363](client/src/pages/CashFlow.jsx:363) — `p.cash_velocity.toFixed(2)`

Given the geofence work, a user with location permission denied or a device that returns a partial fix is a realistic path to hitting these.

### React keys

116 uses of `key={index}` / `key={i}`. Functionally fine for static lists; causes state to attach to the wrong row when a list is sorted, filtered, or has rows deleted — a classic "I edited row 3 and row 5 changed" report. Worth switching to `key={row.id}` in any list that supports delete or re-sort.

## 6. Limits of this audit

- **Static analysis only.** Nothing was run in a browser and no endpoint was called. Findings are grounded in code, but I have not observed any of them fail for a real user.
- **Pattern sweeps have false positives.** The per-file counts (missing loading state, missing empty state) were derived by keyword search; a page using a differently-named variable would be listed wrongly. The named-and-quoted findings in sections A, C, and the `.toFixed()` list were verified by reading the code.
- **Not covered:** business-logic correctness (does the payroll math match mam's rules, do the approval chains route correctly), database schema/index review, the `client/dist` build output, test coverage, and third-party dependency vulnerabilities.
- **Overlap with prior work.** Section A restates findings from the earlier whole-backend security audit; this pass confirms they remain unfixed on this branch.
