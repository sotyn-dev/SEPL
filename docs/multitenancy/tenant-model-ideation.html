1The one big idea

Everything below rests on a single picture. If you remember only this, you'll understand the rest.

🍽️

Think of a restaurant chain:

  • The recipe book = our software (the code). Everyone shares the same recipe book.
  • The ingredients = the data (each company's customers, orders, files).
  • Each company gets its own private pantry that nobody else can see or touch.

Same recipes for all; every company cooks with its own private ingredients. That one idea answers almost every question about multi-company design.

2The two-layer model

The design is built as two clearly separated layers. Keeping them apart is the core principle — mixing them is where multi-tenant systems go wrong.

Layer 1 Platform / Orchestration — the “management” layer
The company-of-companies control room. It decides who the tenants are, what plan / price each is on, which features they're allowed, and it creates new companies. Run and seen only by us (the super-admin).
▾ governs ▾
Layer 2 Per-Tenant Settings — each company's own world
Inside one company: its own users, roles & permissions (RBAC), its own preferences, and its own data. Each company runs its own house — including whether it even uses an “admin” role or its own custom scheme.
In one line Layer 1 decides what a company is allowed to have; Layer 2 decides how that company runs itself inside those allowances.

3A separate pantry per company DECIDED

How each company's data is kept apart.

Every company gets its own separate database and its own file storage — its own labelled cupboard. One company can never see into another's cupboard, even by accident. This is the safest design and, happily, our app is already built this way, so it's a natural fit rather than a rebuild.

✓ Why this is good

  • Strong privacy — data can't leak between companies.
  • Backups, cleanup and disk usage are naturally per company.
  • One company's problem stays contained to that company.

✗ What we deliberately avoid

  • One giant shared database with a “company” tag on every row.
  • That path risks cross-company leaks and is a far bigger, riskier rebuild.

Where the files live — and keeping the VPS from filling up

Two things eat disk space: the database (records) and uploaded files (photos, attachments, voice notes, documents). Today both sit on the VPS's own disk. As companies and their files pile up, that fixed disk becomes the ceiling — and VPS disk is small and relatively costly. So the design treats storage as a swappable layer, which is a major safeguard for scaling to many companies.

Technical note — the storage “seam” (for those who want the mechanics)
  • A storage switch, not a rewrite. One setting — STORAGE_DRIVER = local | s3 — decides where uploaded files physically live. local = the VPS disk (today); s3 = cloud object storage. The application code is identical either way.
  • Object storage = effectively unlimited, cheap, pay-as-you-go. Services like Cloudflare R2, Backblaze B2 or Amazon S3 hold files outside the VPS. This lifts the disk ceiling and grows with us — the core disk-space + scalability lever.
  • The database doesn't change. Records still store a plain path such as /uploads/site-chat/photo.jpg. Whether that resolves to the VPS or the cloud is decided by the switch — so turning on cloud storage is a configuration flip (“just add a key”), not a code migration.
  • Company identity carries into the cloud. Each company's files sit under their own prefix in the bucket, e.g. tenant_sepl/uploads/… — the same “separate pantry” idea, now in cloud storage.
  • Disk safeguards already in place. Backups are compressed into one .zip per run and auto-pruned; databases are periodically compacted; orphaned uploads are swept into a reversible quarantine. Cloud offload is the next lever stacked on top of these.

Why it matters here: building storage as a swappable layer now means we can move files to cheap cloud storage later — the day volume or budget calls for it — without touching the app. Worth weighing as part of the model. SEAM READY · SWITCH LATER

4Two kinds of “settings” people confuse

“Can this person do X?” actually has two gates. Both must say yes.

GateQuestion it answersWho sets it
Entitlement
(the plan)		 Is this feature/module included in the company's plan at all? Layer 1 — us
Permission (RBAC)
(the role)		 Within the company, is this user's role allowed to do it? Layer 2 — the company

Effective access = entitled and permitted. Example: the Solar module must be in the company's plan (entitlement) and the logged-in user's role must allow it (permission). Good news: our app already has a full “module + role permission” system, so this is a layer added on top of something that exists — not a new invention.

5What lives where — and why a restore stays safe

A subtle but important rule that protects revenue and trust.

Because the plan (entitlements) is a commercial decision and the company's own settings are operational, they must live in different places:

InformationLives inRestored with company data?
Plan & allowed features (entitlements)Platform (Layer 1)No — kept separate
Users, roles, permissions, preferencesThe company's own DB (Layer 2)Yes — belongs to them
The trap we're avoiding If a company's allowed features were stored inside their own database, then restoring an old backup could quietly bring back features they no longer pay for — overriding the current plan. So the “what you're allowed” always lives in the platform layer and is checked live. Restoring a company's data can only bring back their information, never their commercial allowance.

6Custom work for just one company

Sometimes one company needs something bespoke. Here's the rule that keeps that sane.

📖

Bespoke work is a clearly-labelled special chapter in the one shared recipe book — never a separate book. Everyone still has one book; that chapter simply only opens for the company it's meant for and stays closed for everyone else.

Why never a separate copy of the software? The day you print a slightly different book per company, every future fix must be redone in every book by hand — they drift apart and become unmaintainable.

Rule of thumb: differences between companies live in their settings, their data, or a clearly-scoped switchable module — never in a separate copy of the software.

7How a developer reproduces one company's issue

Fixing a company-specific problem — safely, without touching real customer data.

A developer can recreate a company's setup on their own laptop, using fake practice data. This reproduces the common kind of issue (“who can see what,” feature/permission quirks) with zero real customer data leaving the server.

  1. Pull the company's setup — through the orchestration dashboard, a developer with a special limited permission clicks “Export dev config” for that company. It bundles the roles, permissions and settings (with all passwords/secrets stripped out).
  2. Load it locally — a small script builds a fresh local copy, applies that setup, and creates fake test users for each role.
  3. Work as any role — the developer logs in as, say, that company's “viewer” role, sees exactly what they see, reproduces the problem, and fixes it.
Safe by design Only the setup is copied (no customer records, no secrets), and every export is logged (who pulled which company, when). For the rarer bug caused by one odd data record, a specially anonymised data sample is used instead — only when authorised.

8Adding a new company VISION

The end goal: onboarding should feel like flipping switches, not a technical project.

A super-admin orchestration panel where we can create a company, choose its plan, turn features on/off, and (later) drive pricing & feature-selection screens. The aim is that adding a company is settings-managed — its database and starting setup build themselves, and its nightly backups start automatically. No manual technical labour per company.

The one design choice this depends on How companies “run” affects how easy automatic onboarding is — this is still OPEN. See the next section.

9What's decided vs. still open

So reviewers know where opinions actually change the outcome.

Decided DECIDED

  • Separate database + files per company (the private pantry). Not one shared database.
  • Two-layer model: platform allowances on top, each company's own RBAC underneath.
  • Allowances (the plan) live in the platform layer, checked live — never inside a company's own database.
  • Bespoke work = a switchable module in the one codebase — never a separate copy.
  • Storage is a swappable layer — files can move from VPS disk to cheap cloud storage (S3/R2) later by a config switch, with no code change. Disk-saving groundwork (compressed backups, DB compaction, upload quarantine) is already in place.

Still open — your input wanted OPEN

  • How companies run (the big one): one shared program serving all companies, versus one separate program per company. This mainly affects how automatic onboarding can be and how isolated companies are from each other. It can also be decided later, when the second company actually arrives.
  • Pricing & feature-selection screens — a later phase; shape not yet designed.

Important groundwork (before company #2)

  • Tidy up a few places where rules are “hard-wired” in code today, so per-company features stay reliable.
  • Add a simple “which version is this database on” stamp and make setup steps fail loudly instead of silently, so many companies' databases can be kept in step safely.
  • Roll changes out to one company first (a canary) before all.
